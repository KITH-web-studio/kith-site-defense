# Локальный MCP и журнал прокси

[Документация](README.md) · [Сценарий расследования](recovery.md) · [Справочник WP-CLI](wp-cli.md)

MCP-клиент запускает Site Defense как локальный процесс WP-CLI и обменивается с ним сообщениями через stdio. Команда должна выполняться там, где доступны файлы WordPress, подключение к базе и, при необходимости, журнал прокси.

## Подключение клиента

1. Выделите WordPress-пользователя для расследования. Добавьте право командой `wp user add-cap investigator site_defense_investigate`. У администратора уже есть доступ через `manage_options`.
2. В настройках MCP-клиента добавьте сервер stdio. Ниже конфигурация для клиентов с ключом `mcpServers`. Замените путь к WP-CLI, путь к WordPress и имя пользователя.

```json
{
  "mcpServers": {
    "site-defense": {
      "command": "/usr/local/bin/wp",
      "args": [
        "--path=/srv/www/wordpress",
        "--user=investigator",
        "--quiet",
        "site-defense",
        "mcp"
      ]
    }
  }
}
```

3. Перезапустите подключение и проверьте, что клиент видит три инструмента. Чтобы отключить доступ, выполните `wp user remove-cap investigator site_defense_investigate`. Изменение проверяется при следующем вызове инструмента.

Для клиента или агента запускайте процесс от системного пользователя с доступом только к нужному стенду. `--user` выбирает роль внутри WordPress. Доступ к оболочке, файлам и базе регулируется правами ОС. Вывод расследования может содержать внутренние пути и идентификаторы. Передавайте его только тем, кто участвует в расследовании. Рассматривайте содержимое записей и журналов как данные из потенциально скомпрометированного источника.

## Инструменты

| Инструмент | Аргументы и результат |
| --- | --- |
| `site_defense_investigate` | `hours` от 1 до 168, по умолчанию 24. `limit` от 1 до 200 записей на источник, по умолчанию 80. Возвращает хронологию, гипотезы о точке входа, источники свидетельств и `cleanup_targets`. |
| `site_defense_prepare_cleanup` | `targets` содержит от 1 до 10 точных ID из `cleanup_targets` текущего отчёта. Сохраняет предложение и возвращает ID плана и его шагов. |
| `site_defense_verify_cleanup` | `plan_id` из подготовленного плана. Сверяет текущее состояние целей, ожидаемые хеши, записи WP-Cron, карантин и сохранённые гипотезы. |

Начните с `site_defense_investigate` и прочитайте основания по каждой гипотезе. Передайте выбранные цели в `site_defense_prepare_cleanup`. Оператор с `manage_options` просматривает шаги и применяет или отменяет их через WP-CLI. Затем снова вызовите `site_defense_verify_cleanup`. [Предпросмотр, применение и откат](recovery.md#план-очистки)

## Журнал обратного прокси

Чтобы сверять отдельный запрос, прокси должен создавать собственный ID, записывать его в журнал сайта и передавать тот же ID в PHP. Пример для Nginx с FastCGI. В контексте `http` добавьте следующую конфигурацию.

```nginx
map $request_uri $sd_log_path {
    ~^(?<sd_path_before_query>[^?]+) $sd_path_before_query;
    default /;
}

log_format site_defense escape=json
    '{"time":"$time_iso8601","method":"$request_method","path":"$sd_log_path",'
    '"status":$status,"sd_request_id":"$request_id"}';
```

Добавьте `access_log /var/log/nginx/site-defense.jsonl site_defense;` в `server` этого сайта. В существующий PHP-обработчик рядом с другими параметрами FastCGI добавьте `fastcgi_param SITE_DEFENSE_REQUEST_ID $request_id;`. Используйте ID, сгенерированный сервером. Оставьте журнал за пределами веб-каталога, с доступом на чтение для пользователя WP-CLI.

Добавьте `--access-log=/var/log/nginx/site-defense.jsonl` в аргументы MCP-сервера. Тот же отчёт можно получить отдельно.

```sh
wp --user=investigator site-defense investigate --hours=24 --access-log=/var/log/nginx/site-defense.jsonl
```

Читаются последние 512 КиБ журнала. Поддерживается также стандартный combined-журнал сайта для выборки подходящих запросов, например POST к странице входа или к файлам плагинов. Для точной связи нужен формат с ID запроса.

## Как читать связь WAF и прокси

Для каждого ID в `request_correlation.requests` указаны `status`, `confirmed_sources`, `sources` и `gaps`.

| Статус | Что обнаружено |
| --- | --- |
| `confirmed` | Совпадает ID, и проверка не нашла противоречий. Недостающие поля указаны в `gaps`. |
| `waf_only` | Запись есть в WAF. В прочитанной части журнала прокси соответствия нет. |
| `proxy_only` | Запись есть только в журнале прокси. Запрос мог пройти без совпадения с правилами. |
| `conflict` | Источники расходятся, например по маршруту, времени, коду ответа или из-за повторяющегося ID. |

Даже при `confirmed` оценивайте другие свидетельства о проникновении. Например, HTTP 403 вместе с событием WAF подтверждает блокировку этого запроса. При пробеле проверьте, передаёт ли прокси ID, попало ли событие в последние 512 КиБ и успел ли обработаться буфер раннего WAF.
