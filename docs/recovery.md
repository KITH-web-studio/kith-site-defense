# Расследование и восстановление

[Документация](README.md)

## Если есть признаки взлома

1. Сохраните копию базы, файлов и журналов хостинга. При подозрении на заражение запускайте WP-CLI и MCP на изолированной копии, поскольку WP-CLI загружает код активных компонентов.
2. Во вкладке **Инциденты** просмотрите события вокруг первого замеченного изменения. При необходимости включите временный режим инцидента после просмотра плана.
3. Запустите [сканирование файлов и аудит базы](scanning.md). Для разбора входа соберите отчёт расследования и, если есть, отдельный журнал прокси.
4. Подготовьте план выбранных действий. Проверьте цели и резервные копии перед применением.
5. После очистки повторите проверки и отдельно устраните вероятный путь проникновения. Например, обновите затронутый компонент или отзовите скомпрометированные учётные данные.

## Режим инцидента и хронология

Во вкладке **Инциденты** задайте срок от 5 минут до суток и нажмите **Просмотреть план**. Можно оставить поля сессий и паролей приложений пустыми.

При подтверждении режим временно ограничивает установку и загрузку плагинов и тем и работу редактора файлов WordPress. Плагин отзывает только выбранные сессии и пароли приложений. Отзыв необратим. По окончании срока или после остановки режима временные ограничения снимаются.

Хронология связывает привилегированные входы, изменение прав, изменения компонентов и действия с файлами и планами. В админке показываются последние 50 событий за сутки. Всего хранится до 10 000 событий за последние 14 дней. Сохраните нужный интервал отдельно.

```sh
wp site-defense response preview --minutes=60
wp site-defense response start --minutes=60
wp site-defense response status
wp site-defense timeline --hours=24 --limit=1000 > site-defense-timeline.json
```

Храните экспорт вне каталога, доступного через веб-сервер.

## План очистки

Через WP-CLI выберите администратора сайта и получите отчёт. Вместо имени `admin` используйте свой логин WordPress.

```sh
wp --user=admin site-defense investigate --hours=24 --limit=80
wp --user=admin site-defense cleanup prepare TARGET_ID
wp --user=admin site-defense cleanup show PLAN_ID
```

В `cleanup_targets` найдите идентификаторы нужных целей. `cleanup prepare` принимает до 10 ID через запятую без пробелов. Для работы через MCP выберите цели и вызовите `site_defense_prepare_cleanup`. План фиксирует свидетельства и выбранные шаги. [Как подключить MCP и прочитать отчёт](mcp.md)

| Тип шага | Что проверяется перед изменением |
| --- | --- |
| Карантин | Путь и SHA‑256 выбранного файла. |
| Официальное восстановление | Путь, SHA‑256 и точная версия компонента из отдельного предпросмотра. |
| WP-Cron | Хук, время, ключ аргументов и хеш события. Хуки WooCommerce, Action Scheduler и Site Defense исключены. Для старых отчётов запустите свежий аудит. |
| HTML в базе данных | Тип записи, хеш текущего поля и выбранный фрагмент HTML. |

### Предпросмотр, применение и отмена

Для шага HTML в базе выполните `cleanup preview`, чтобы увидеть экранированные фрагменты и хеши поля. Для официального восстановления выполните `repair preview STEP_ID` и передайте возвращённый ID как `--repair-preview=PREVIEW_ID` при применении. Для применения и отмены требуется право `manage_options`. WP-CLI запрашивает подтверждение каждого выбранного шага.

```sh
wp --user=admin site-defense cleanup preview PLAN_ID STEP_ID
wp --user=admin site-defense cleanup apply PLAN_ID STEP_ID
wp --user=admin site-defense cleanup verify PLAN_ID
wp --user=admin site-defense cleanup undo PLAN_ID STEP_ID
```

Аудит предлагает очистку полных исполняемых тегов `<script>` и `<meta http-equiv="refresh">` в содержимом и отрывках записей и страниц, описаниях товаров WooCommerce и обычных комментариях к записям и страницам. Поля ограничены 128 КиБ. На одно поле показывается до 12 фрагментов, за проход — до 200. Несколько выбранных фрагментов одного поля объединяются в один шаг. Точное место заменяется пустым HTML-комментарием, который сохраняет границу соседнего текста. Параметры и метаданные WordPress, структурированные значения, заказы, заметки заказов и таблицы HPOS исключены из очистки.

Если поле изменилось после подготовки плана или выполнения шага, операция останавливается. Отмена применённого шага возвращает сохранённый файл, исходное поле или событие в его прежнее время. Проверьте, какой код вернётся, прежде чем подтверждать.

## Проверка после очистки

`cleanup verify PLAN_ID` и MCP-инструмент `site_defense_verify_cleanup` показывают ожидаемое и фактическое состояние выбранных целей. Для файлов и полей сверяются хеши и сохранённая копия. Для WP-Cron проверяется, исчезло ли выбранное событие и не было ли оно перенесено.

Статус вероятной точки входа показывается отдельно от результата действий. Обновлённый файл или удалённый скрипт могут пройти проверку шага при всё ещё уязвимой версии компонента. Отчёт сверяет данные о версиях локально и читает последние сохранённые находки. Для свежего результата повторите сканирование и аудит. В WooCommerce также проверьте тестовый заказ и платёжный колбэк на стенде.

## Восстановление доступа

Для остановки режима инцидента и снятия обязательной 2FA используйте WP-CLI.

```sh
wp site-defense response stop --yes
wp site-defense policy disable --yes
```

Снятие обязательной политики сохраняет индивидуально настроенную 2FA. После отзыва сессий нужно снова войти. Если Site Defense мешает загрузке WordPress, отключите его из консоли. При необходимости исключите его из загрузки WP-CLI для этой операции.

```sh
wp plugin deactivate site-defense --skip-plugins=site-defense
```

Если WP-CLI недоступен, а смена адреса входа лишила доступа, переименуйте каталог `site-defense` в `wp-content/plugins` через файловый менеджер хостинга и войдите через `/wp-login.php`. Для неисправности раннего загрузчика отдельно проверьте управляемую запись `auto_prepend_file` в `.user.ini` или настройку хостинга. [Ранняя защита](protection.md#ранняя-защита)
