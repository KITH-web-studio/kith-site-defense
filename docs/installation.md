# Установка и обновление

[Документация](README.md)

## Требования

| Возможность | Требования |
| --- | --- |
| Установка | WordPress 6.8+, PHP 8.2+, один сайт без Multisite. |
| Подписанные обновления и импорт базы, WAF или сигнатур | PHP Sodium. |
| Настройка двухфакторной аутентификации | HTTPS для входа и админки, PHP Sodium. |
| Восстановление файла из официального архива | PHP ZipArchive и доступ к WordPress.org. |
| Команды и MCP | WP-CLI. Для MCP также нужен локальный клиент с транспортом stdin/stdout. |

WooCommerce устанавливается по необходимости. Проверки обновления с `1.0.0-rc.2` на `1.0.0` прошли на WordPress 6.8 с PHP 8.2.35 и на WordPress 7.1.4 с WooCommerce 11.3.0 и HPOS.

## Установка через WordPress

1. Откройте [стабильный выпуск](https://github.com/KITH-web-studio/kith-site-defense/releases/latest) и скачайте приложенный `site-defense.zip` из раздела **Assets**. Выбирайте архив с этим именем. GitHub также автоматически добавляет архив исходников репозитория.
2. В админке откройте **Плагины → Добавить плагин → Загрузить плагин**.
3. Загрузите ZIP, нажмите **Установить**, затем **Активировать**. В боковом меню появится **Site Defense**.
4. При ошибке размера файла проверьте лимит загрузки WordPress и настройки PHP `upload_max_filesize` и `post_max_size`.

Через WP-CLI выполните эти команды из каталога WordPress.

```sh
wp plugin install /path/to/site-defense.zip --activate
wp site-defense status
```

Админка использует язык профиля пользователя WordPress. Если в профиле выбран язык сайта, применяется локаль сайта. Заголовки уязвимостей сохраняют язык исходной базы.

## Первые проверки

1. В **Защите** просмотрите настройки HTTPS, редактирования PHP и обратного прокси. Ограничение попыток входа, WAF и быстрый контроль ключевых файлов включены при установке.
2. Во вкладке **Файлы** нажмите **Запустить сканирование**. Посмотрите число проверенных файлов, находки и отчёт о пропусках после завершения.
3. Во вкладке **Проверка базы данных** запустите аудит. Сверьте найденные привилегированные аккаунты со своим списком администраторов.
4. Во вкладке **Уязвимости** запустите сверку версий. При необходимости включите WPVulnerability.
5. Если подключаете доставку, отправьте тестовое сообщение из вкладки **Уведомления** и проверьте его получение. [Настройка каналов](notifications.md)

Раннюю фильтрацию, обязательную 2FA и смену адреса входа настраивайте после базовой проверки сайта и доступа к WP-CLI. Для магазина полезно выполнить тестовый заказ после смены режима WAF. [Настройки защиты](protection.md)

## Обновление плагина

Начиная с `1.0.0-rc.2` обновление устанавливается из **Консоль → Обновления** или **Плагины → Установленные плагины**. При более ранней версии скачайте актуальный `site-defense.zip` и загрузите его через форму установки, подтвердив замену.

По умолчанию плагин проверяет стабильный канал. Чтобы получать предварительные выпуски, откройте **Site Defense → Защита → Канал обновлений плагина**, выберите **Стабильные выпуски и кандидаты (RC)** и сохраните. Возврат на стабильный канал влияет и на установку уже показанных RC. Версия на сайте меняется при установке более нового подходящего выпуска.

```sh
wp plugin update site-defense
```

При желании включите автообновления в списке плагинов WordPress. Site Defense получает сведения о публичном релизе и проверяет подпись манифеста, размер ZIP и SHA‑256 архива. Если проверка завершается ошибкой, WordPress сообщает о сбое и сохраняет установленную версию. Сайту нужны HTTPS-доступ к GitHub и PHP Sodium. Обновление базы уязвимостей настраивается отдельно. [Источники уязвимостей](protection.md#источники-уязвимостей)

## Восстановление доступа

Отключить плагин можно в списке плагинов или через WP-CLI.

```sh
wp plugin deactivate site-defense
```

Деактивация снимает фильтрацию входа и отключает управляемую конфигурацию ранней защиты. Копии в карантине хранятся в базе WordPress и доступны после повторной установки. Если проблема только в режиме инцидента или политике 2FA, используйте [команды восстановления доступа](recovery.md#восстановление-доступа).
